# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

Developers who run coding agents on their own repositories, starting with the repo owner.
They open `weave explore` in three situations, all confirmed:

- **Checking an agent's work.** An agent says it is done; the person wants to know what
  is broken, what a change reaches, and what is still open in the spec change.
- **Planning the next work.** Picking the next change or task and seeing where proof
  (tests) is missing.
- **Orienting in a repo.** Learning what screens exist, what an endpoint touches, where a
  table is used, often in a codebase of several hundred files.

Agents never read the page; they use the MCP server. Every choice on the page serves a
person reading.

## Product Purpose

weave indexes a repository into one graph: screens call HTTP endpoints, endpoints are
handled in modules, modules use tables, plus tests, requirements and spec-change records.
The explorer is that graph made readable for people. Success: a person who opens the page
knows in ten seconds whether the repo is healthy and what to do next, and can move from
"what next" to the map to one item and back without getting lost.

## Positioning

The map spans both halves of the contract (frontend call sites and backend routes) and is
honest about what it could not parse: coverage is measured and printed. An edge is either
exact or inferred, and the page never hides which.

## Operating Context

- Generated by `weave explore`; one self-contained HTML file opened from disk, offline.
- `weave explore --all` puts every registered project in one file with a switcher.
- Real sizes: from a 25-file repo (5 endpoints) to QR-gent (761 files, 196 endpoints, 33
  screens, 46 tables, 87 change records, ~2,000 nodes).
- The same facts are served to agents as `context`, `impact`, `plan`, `changes`, and the
  CLI gate `weave check`; the page should use the same vocabulary.

## Capabilities and Constraints

- No framework, no build step, no webfonts, no runtime network, no daemon. CSS and JS are
  embedded from `internal/weave/assets/`; the shell markup lives in `render.go`.
- The payload contract (`explore.go`) is shared with tests; changing it means changing
  both.
- Must keep: global search, URL hash state (back/forward, pasted links), keyboard access,
  light/dark/system theme, the multi-project switcher, and complete lists of screens,
  endpoints, tables, changes and problems.
- Output is checked by a golden test (`testdata/explore.golden.html`).

## Brand Commitments

Name is lowercase `weave`. Voice: plain, factual, short; relations are written as words
("Called from these screens"), never as graph edge names.

## Evidence on Hand

Real graphs from this repo and from a private 761-file monorepo. No customers, testimonials or benchmarks
beyond those in README.md and docs/DESIGN.md.

## Product Principles

1. Health first, then the next action, then the map.
2. Never lose the reader: every view says where it is and how to get back.
3. Show what was measured, label what was inferred, print nothing computed only for show.
4. A gap in proof is information, not alarm; red is reserved for what `weave check` fails.

## Accessibility & Inclusion

WCAG 2.2 AA contrast in both themes, full keyboard use, usable at 375 px wide with no
horizontal scroll, and respects reduced motion.
